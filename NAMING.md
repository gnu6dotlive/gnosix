# Naming

## Canonical public names

Use these spellings in authored public copy:

- `gnosix` — project/system identity.
- `gnos.ux` — native product presentation and UX domain.
- `in.gnu.os` — system-service/authority identity.
- `gnusnip` — capture/snip product identity.
- `gnoshow` — rear-plane/wallpaper rendering component.
- `gnu6.live` — public web/service surface where relevant.
- `gnu.in.labs` — legal/company identity where relevant; it is not required as a GitHub organization namespace.

The canonical GitHub project namespace is `tension-atoi/gnosix`.

## Technical identifiers

Crate names, environment variables, protocol constants, historical filenames, evidence identifiers, and machine-readable keys may use casing or legacy tokens required by their technical contract. Do not bulk-search-and-replace identifiers merely to make them resemble display copy.

Examples such as `GNOSIX_R13_QUALIFY_ACTIVE_WORKSPACE` are protocol or evidence identifiers, not branding guidance.

## Historical names

Former names may appear only when a document is explicitly describing historical provenance, a donor, a superseded artifact, or a byte-preserved record. Historical spelling is not current product naming.

A new public document should not reintroduce former platform names as aliases, headings, or explanatory shortcuts.

## Repository naming rule

Public prose uses current names. Machine contracts preserve exact identifiers. Evidence preserves provenance. When those goals conflict, add explicit context rather than rewriting historical bytes.
